# تقرير التدقيق الوظيفي لنظام المصادقة

مرحلة التدقيق الشامل: تنفيذ واختبار جميع سيناريوهات Authentication والتحقق من
السلوك الفعلي (وليس وجود الكود فقط).

- تاريخ التنفيذ: 2026-10-18
- البيئة: Flutter 3.44.8 / Dart 3.12.2 على Windows 11، بدون جهاز Android أو
  محاكي متصل، وبدون صلاحية على مشروع Firebase.
- حالة الحسم: كل الحالات القابلة للاختبار محليًا تم اختبارها وتنجح (انظر البنود)،
  وما تعذر اختباره موثق صراحة مع سببه والاختبار البديل.

## 1. متطلبات إنشاء الحساب المستخرجة من المشروع

المصادر التي فُحصت: شاشة `register_screen.dart` ونصوصها في ملفات ARB،
`auth_validators.dart`، كيان `app_user.dart`، شاشة الملف الشخصي
`update_profile_screen.dart`، أصول التصميم في `assets/images`، ملفات
Android/iOS للإعدادات، و`README.md`، ومجلد `docs`.

النتيجة:

| الحقل | الحالة في إنشاء الحساب | الدليل |
| ----- | ---------------------- | ------ |
| الاسم الكامل | مطلوب | حقل في شاشة التسجيل + `validateName` |
| البريد الإلكتروني | مطلوب | حقل + `validateEmail` + قاعدة Firebase |
| كلمة المرور | مطلوبة | حقل + السياسة: 8 أحرف + حرف + رقم |
| تأكيد كلمة المرور | مطلوب | حقل + `validateConfirmPassword` |
| رقم الهاتف | **غير مطلوب** | لا وجود له إلا كحقل ملف شخصي في `update_profile_screen.dart` (قيمة تجريبية `01200000000`) ولا يوجد تخزين له |
| الموافقة على الشروط | **غير مطلوبة** | لا يوجد أي نص أو مربع اختيار في المشروع كله |

- لا يوجد إنشاء ملف مستخدم إضافي (لا Firestore ولا Realtime Database في
  المشروع، وهذا قرار موثق في `docs/AUTHENTICATION.md`).
- لا توجد خطوة onboarding خاصة بالحساب؛ شاشات Onboarding الحالية تظهر لمرة
  واحدة عند أول تشغيل للتطبيق قبل شاشة الدخول ولا علاقة لها بإنشاء الحساب.
- لا تُمنح أي صلاحيات أو اشتراكات عند التسجيل؛ لا وجود لمثل هذا المنطق في
  المشروع أصلًا.
- لا تعارض بين المصادر، ولم يُخترع أي حقل جديد ولم يُحذف أي حقل مطلوب.

نموذج البيانات الحالي للمستخدم (`AppUser`): `uid`, `email`, `displayName`,
`photoUrl`, `emailVerified` — وكلها تأتي من Firebase Auth وحده.

## 4. نتائج استعادة كلمة المرور (Forgot / Reset Password)

### ما تم اختباره فعليًا في التطبيق

| الخطوة | النتيجة |
| ------ | ------- |
| فتح الشاشة من "Forgot password?" | ناجح |
| التحقق من صيغة البريد قبل الإرسال | ناجح (لا طلب عند بريد غير صالح) |
| إرسال الطلب وتطبيع البريد | ناجح (اختبار المستودع: البريد يُطبَّع قبل الإرسال) |
| رسالة نجاح محايدة | ناجح: "If an account exists for this email, a reset link has been sent. Check your inbox." |
| عدم إظهار نجاح وهمي عند الفشل | ناجح: عند فشل الشبكة تظهر رسالة الخطأ فقط، والاختبار يؤكد غياب نص النجاح |
| حالات الفشل (شبكة، تجاوز محاولات) | ناجح مع بقاء الشاشة قابلة لإعادة المحاولة |
| منع الطلب المكرر أثناء التنفيذ | ناجح |

### خطوات تجري على صفحة Firebase المستضافة (لا تملك الصفحة أي كود في التطبيق)

الخطوات 2–5 من المطلوب (وصول الرسالة، فتح رابط إعادة التعيين، شاشة كلمة المرور
الجديدة، حفظ كلمة المرور) ينفذها Firebase عبر صفحة الإجراءات المستضافة
(`https://movies-app-3cb31.firebaseapp.com/__/auth/action`) وليست جزءًا من كود
التطبيق، وبالتالي:

- **لا يمكن اختبارها من هذه البيئة**: لا صلاحية على المشروع لفحص القالب أو
  الروابط، ولا وصول لبريد تجريبي لاستلام الرسالة، ولا جهاز/محاكي لفتح الرابط.
- التدفق الافتراضي جاهز بمجرد تفعيل Email/Password في الـConsole، وهذا موثق
  كخطوة يدوية.
- التطبيق **لا** يتعامل مع روابط إعادة التعيين داخل نفسه (لا App Links ولا URL
  Schemes — انظر البند 8)، ولا يسجل المستخدم تلقائيًا بعد إعادة التعيين، فيجب
  أن يعود ويسجل الدخول بكلمة المرور الجديدة يدويًا.

### الحالات السلبية لرابط إعادة التعيين

(رابط غير صالح، منتهي، مستهلك، كلمة مرور غير مطابقة…) كلها تُعالج وتُعرض على
صفحة Firebase المستضافة. التطبيق لا يستدعي `applyActionCode` أو
`confirmPasswordReset` إطلاقًا، لذلك لا يوجد مسار يمكن أن يظهر فيه نجاح زائف
من جهة التطبيق. **لم يتم اختبار هذه الحالات فعليًا** لعدم توفر الصلاحية/البريد.

## 8. الروابط العميقة (Deep Links)

نتيجة الفحص:

- `AndroidManifest.xml`: لا يوجد إلا `MAIN/LAUNCHER`، لا App Links ولا scheme
  مخصص.
- `ios/Runner/Info.plist` وmacOS: لا `CFBundleURLTypes`.
- التطبيق لا يقرأ أي رابط إجراء (لا معالجة لـ`oobCode`).

الخلاصة: تدفق الروابط الحالي هو **الصفحة المستضافة من Firebase** (الافتراضي).
هذا يعمل بدون أي تعديل على التطبيق بمجرد تفعيل المزود، لكنه يعني أن الرابط يفتح
المتصفح وليس التطبيق مباشرة، وأن المستخدم يعود للتطبيق ويسجل الدخول يدويًا.

إذا أراد الفريق فتح التطبيق مباشرة من الرابط (تدفق الروابط العميقة داخل التطبيق)
فهذا قرار منتج يحتاج: إعداد App Links/URL Schemes للمنصة، شاشة إدخال كلمة مرور
جديدة في التطبيق، وربط `oobCode` عبر واجهات Firebase الرسمية، وتعديل قالب
البريد/رابط الإجراء في الـConsole. **لم يُنشأ حل وهمي لهذا**، والخطوات موثقة
كعمل مستقبلي.

**لم يُختبر فتح أي رابط فعليًا** لعدم توفر جهاز ومشروع مُعدّ.

## 9. منهجية التحقق المستخدمة

| المستوى | ما نُفذ |
| ------- | ------- |
| اختبارات وحدات | منطق التحقق من المدخلات (بريد/كلمة مرور/تأكيد/اسم) وتحويل أخطاء Firebase |
| اختبارات المستودع | `FirebaseAuthRepository` مع مصدر بيانات بديل: تطبيع البريد، تسلسل التسجيل، تحويل الأخطاء، تفويض العمليات |
| اختبارات cubits | 6 cubits: حالات التحميل/النجاح/الفشل/التكرار/العدّاد |
| اختبارات واجهات | 4 شاشات: الرسائل، التحميل، تعطيل الأزرار، التنقل، منع الضغط المزدوج |
| اختبارات تكامل | التدفق الكامل على التطبيق الحقيقي: جلسة، دخول، تسجيل، تأكيد، خروج، حذف، عربي/RTL، أحداث متكررة، حفاظ على التفضيلات |
| تحليل ثابت | `flutter analyze`: لا أخطاء ولا تحذيرات من كود المصادقة |
| تنسيق | `dart format` على كل الملفات المضافة/المعدلة |
| بناء | `flutter build apk --debug` و`flutter build apk --release` **ناجحان** بعد إصلاح إعدادات ذاكرة Gradle (انظر البند 10) — الدليل: `build/app/outputs/flutter-apk/app-debug.apk` و`app-release.apk` (‏54.3MB) |
| Emulator | **لم يُستخدم** — Firebase Emulator لا يمكن تشغيله بصلاحيات المشروع الحالية، وتشغيله بدون جهاز/إعدادات لا يعطي قيمة إضافية |
| جهاز حقيقي | **غير متاح** — لا يوجد جهاز Android أو محاكي متصل بالبيئة |
| Firebase فعلي | **غير متاح** — الحساب الحالي بلا صلاحية (403) على المشروع |

لم تُستخدم أي حسابات حقيقية لأعضاء الفريق، ولم تُنشأ أي حسابات في الإنتاج.

## 10. المشكلات المكتشفة والإصلاحات

اكتُشفت خلال التدقيق مشكلة وظيفية واحدة في منطق المصادقة (أول صفوف الجدول)
إلى جانب مشكلات أدوات الاختبار والبناء، وكلها أُصلحت وأُعيد اختبارها:

| المشكلة | السبب الفعلي | الإصلاح |
| ------- | ------------ | ------- |
| التحقق من البريد يفشل أوفلاين ويعرض رسالة عامة | `AuthCubit.refreshUser` كان يبتلع نوع الخطأ ويعيد `null` فقط، فلا تستطيع الشاشة معرفة السبب الحقيقي | إضافة `refreshFailure` إلى `AuthState` وتمريره من الـcubit، وعرض الرسالة الحقيقية (شبكة/تجاوز محاولات/…) في `email_verification_screen.dart` + اختبار جديد |
| كود `configuration-not-found` (حالة المشروع الحالية غير المفعلة) يصل للمستخدم كخطأ عام | مخطط الأخطاء لم يكن يعرف هذا الكود | تحويله إلى `operationNotAllowed` ("This sign-in method is not available right now.") + اختبار |
| فشل 9 اختبارات في أول تشغيل شامل | `pumpFrames` ما كان يعطي إطارًا ثالثًا لإنهاء انتقالات المسارات: الصفحة السابقة تبقى في الشجرة والملقاة لا تُغلق | إضافة الإطار الثالث في `pump_app.dart` |
| ضغط زر "Create account" لا يصل (خارج الشاشة y=624) | مقاس شاشة الاختبار 800×600 والزر أسفل النموذج القابل للتمرير | مساعد `tapButton` يستخدم `ensureVisible` قبل الضغط |
| "Too many elements" عند البحث عن حقل في شاشة إعادة التعيين | شاشة الدخول تحت الجديدة ما زالت في الشجرة أثناء التمرير | حصر البحث داخل `ResetPasswordScreen` |
| اختبار الضغط المزدوج على "Login" يفشل | أثناء التحميل يُستبدل نص الزر بمؤشر | الضغطة الثانية تستهدف الزر نفسه |
| تنبيه `curly_braces_in_flow_control_structures` | سطر `if` بعائد على سطرين في `auth_validators.dart` | إضافة أقواس (الكود المصدري) |
| فشل بناء Android الأول: `Could not find ...firebase-common:.` | انقطاع مؤقت في تنزيل الـBOM أثناء تنفيذ متزامن لأدوات Flutter المتعددة | إعادة البناء بعد تنظيف |
| فشل البناء: `Could not close incremental caches` ثم `Failed connecting to the daemon` | `org.gradle.jvmargs=-Xmx8G` على جهاز بذاكرة 7.6GB: عملية Kotlin compile daemon لا تستطيع الإقلاع أصلًا، ثم تعذر إغلاق ملفات الـincremental cache | تعديل `android/gradle.properties`: خفض الذاكرة إلى 3G + `kotlin.compiler.execution.strategy=in-process` + `kotlin.incremental=false` — والبناء بعدها ناجح |

## 11. ما تم التحقق منه على Firebase فعليًا

| البند | الحالة |
| ----- | ------ |
| قيم Android/iOS/macOS في `firebase_options.dart` | مأخوذة من ملفات الإعداد الرسمية الموجودة في المستودع (لم تُعدَّل) |
| اتصال حقيقي بالمصادقة من التطبيق | **لم يحدث** — لا جهاز/محاكي؛ كل اختبارات التطبيق على مستودع بديل |
| استجابة المشروع الحية لطلبات المصادقة | **فُحصت عبر REST في 2026-10-18** (بدون أي حسابات حقيقية): المشروع `movies-app-3cb31` يرد `CONFIGURATION_NOT_FOUND` على `accounts:signInWithPassword` و`accounts:createAuthUri` |
| تفعيل Email/Password في المشروع | **تحقق حيّ: غير مُفعَّل** — وبالأدق: خدمة Authentication نفسها غير مهيأة؛ المطلوب أولًا `Authentication → Get started` ثم تفعيل المزود |
| وصول رسالة إعادة التعيين أو التحقق | **لم يُتحقق** — لا بريد تجريبي ولا صلاحية |
| إعدادات قالب البريد ورابط الإجراء | **لم تُفحص** — 403 من Firebase CLI |
| Web API key | **مفقود** — Web/Windows/Linux تطلق `UnsupportedError` حتى توليد الإعدادات |

## 12. الإعدادات التي تحتاج تدخلًا يدويًا

1. تفعيل خدمة المصادقة ثم Email/Password: Firebase Console → Authentication →
   **Get started** → Sign-in method → Email/Password → Enable.
   (الفحص الحيّ أثبت أن الخدمة غير مهيأة أصلًا على المشروع.)
2. مراجعة نطاق رابط إعادة التعيين وقالب البريد إذا أردتم تخصيصهما.
3. `flutterfire configure` لحساب يملك الصلاحية لتوليد إعدادات Web/Windows.
4. تجربة يدوية على جهاز Android حقيقي لكل التدفقات (تسجيل → تأكيد → دخول →
   خروج → نسيت كلمة المرور → حذف).
5. تجربة استلام رسالة إعادة التعيين فعليًا والضغط على الرابط مع حساب تجريبي.

## 13. المخاطر والمهام المتبقية

1. **بيئة البناء**: **أُصلح** — `android/gradle.properties` كان يطلب `-Xmx8G`
   وهذه البيئة بذاكرة 7.6GB، فكان Kotlin daemon يفشل بالإقلاع. الآن القيم
   `-Xmx3G` مع `kotlin.compiler.execution.strategy=in-process` و
   `kotlin.incremental=false`، والبناء ناجح. (كما ينبغي التفكير في إزالة ملف
   `temp/` غير المتعقب من آلة التطوير أو إضافته إلى `.gitignore` حتى لا يُرفع
   بالخطأ.)
2. **لا جهاز/محاكي** في هذه البيئة: كل نجاحات الواجهة مثبتة باختبارات آلية وليس
   بتجربة جهاز فعلي.
3. **الحذف الحسابي والملف الشخصي**: "Update Data" في شاشة الملف الشخصي لا يزال
   `TODO` لأنه يحتاج قرار قاعدة بيانات.
4. **الروابط العميقة**: التطبيق لا يفتح الروابط داخليًا (تدفق الصفحة المستضافة
   مقصود)، وأي تغيير قرار منتج.
5. **حسابات اختبار**: لا توجد حسابات اختبار مخصصة في المشروع؛ أي اختبار حقيقي
   مستقبلي يجب أن يستخدم حسابات test مخصصة كما اشترطت المهمة.

## 14. التحقق من تكامل Firebase (فحص شامل للإعدادات)

فُحص التكامل خطوة بخطوة (وليس مجرد وجود الملفات):

| الفحص | النتيجة |
| ----- | ------- |
| الحزم في `pubspec.yaml` | `firebase_core: ^3.12.1` و`firebase_auth: ^5.7.0` — الواجهات الرسمية فقط |
| التهيئة في نقطة الدخول | `main.dart`: `WidgetsFlutterBinding.ensureInitialized()` ثم `Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform)` |
| `android/app/google-services.json` مقابل `applicationId` | متطابقان (`com.example.movies_app`)، وبناء الـAPK نفسه يمر عبر مزود Google Services فيتحقق من التطابق |
| `google-services.json` مقابل `firebase_options.android` | مطابقة حقلاً بحقل: projectId وsenderId وappId وapiKey وstorageBucket |
| `ios/Runner/GoogleService-Info.plist` مقابل `firebase_options.ios` | مطابقة: GOOGLE_APP_ID وPROJECT_ID وBUNDLE_ID وGCM_SENDER_ID |
| `macos/Runner/GoogleService-Info.plist` مقابل `firebase_options.macos` + `AppInfo.xcconfig` | مطابقة كاملة (نفس معرّف تطبيق iOS مستخدم لـmacOS بنفس الـbundle) |
| مرجعية الـplist في مشروع Xcode | `GoogleService-Info.plist in Resources` موجود في مشروعي iOS وmacOS |
| معالجة Google Services أثناء البناء | توليد `values.xml` في `build/app/generated/res/google-services/` بالقيم الصحيحة (app id وsender id وproject id والبكت) |
| الـmanifest النهائي | `FirebaseInitProvider` و`android.permission.INTERNET` في manifest النسختين (debug وrelease) المُحزَّمتين، ومسجّلات `FlutterFirebaseAuthRegistrar` و`FlutterFirebaseCoreRegistrar` و`FirebaseAuthRegistrar` في الـmanifest المُدمج |
| Web/Windows/Linux | غير مهيأة عن قصد: `DefaultFirebaseOptions.currentPlatform` يطلق `UnsupportedError` برسالة إرشادية حتى يولدها من يملك الصلاحية |
| تهيئة وقت التشغيل الفعلية | **لم تُختبر على جهاز** — لا جهاز/محاكي متاح؛ أقوى دليل بيئي متاح هو نجاح البناء ووجود مزوّد التهيئة في الـAPK |
| بيانات دخول مكتوبة يدويًا في الكود | **لا يوجد** — `FirebaseAuth.instance` تُستخدم فقط في `auth_scope.dart` (نقطة التركيب)، ولا توجد كلمات مرور أو برامج وهمية في `lib/` |

استنتاج: الإعدادات متطابقة بلا تعارض أو قيمة ناقصة على Android وiOS وmacOS،
والشرط المتبقي الوحيد هو **تفعيل خدمة Authentication نفسها على المشروع** (Get
started) ثم تفعيل مزود Email/Password — وقد أُثبت بالفحص الحيّ أن الخدمة غير
مهيأة بعد — ثم تجربة فعلية على جهاز.
